# 개발

빌드하고, 테스트하고, 변경을 확인하는 방법.

## 필요한 것

| 도구 | 버전 |
|---|---|
| JDK | 21 |
| Gradle | 9.6.1, 함께 들어 있는 래퍼로 |
| IntelliJ IDEA | 2025.1 이상, 내장 브라우저가 포함된 JetBrains Runtime |

## 검증

| 명령 | 확인해주는 것 |
|---|---|
| `./gradlew test` | 동작, 계층 규칙, 바깥과의 계약 |
| `./gradlew build` | 컴파일과 패키징 |
| `./gradlew koverVerify` | 순수 계층이 계속 덮여 있는지 |
| `./gradlew verifyPlugin --rerun-tasks` | 지원하는 모든 IDE 판에서 플러그인이 로딩되는지 |
| `./gradlew runIde` | 플러그인이 설치된 샌드박스 IDE. 테스트로 닿지 않는 부분을 위해 |

`test`와 `build`는 모든 변경에서 돌립니다. `verifyPlugin`은 IDE 다섯 판을 내려받아 확인하느라 몇 분씩
걸리므로, 작업 하나를 마칠 때와 `plugin.xml`을 고친 커밋에서 돌립니다. 잘못된 클래스 이름은 그때가
아니면 플러그인이 로딩에 실패할 때까지 드러나지 않습니다.

지속적 통합은 pull request와 `main` 푸시에서 `test`, `build`, `verifyPlugin`을 돌립니다.

## 테스트 규칙

### 도구

Kotest의 `BehaviorSpec`을 씁니다. given, when, then이 관례가 아니라 문법으로 강제됩니다. Instancio는
관심 없는 필드를 채웁니다. Kover는 순수 계층을 측정합니다.

Instancio는 `instancio-junit`이 아니라 `instancio-core`로 씁니다. Kotest는 JUnit 플랫폼 위에서 자체
엔진으로 돌기 때문에 JUnit Jupiter 확장은 동작하지 않습니다.

JUnit 4가 테스트 실행 경로에 있습니다. IntelliJ 플랫폼 파일이 그 클래스를 참조해서, 없으면 Gradle 테스트
작업자가 시작조차 못 합니다. 옛 테스트가 발견되지 않도록 vintage 엔진은 일부러 빼두었습니다.

### 이 저장소에서 F.I.R.S.T.

| 원칙 | 여기서의 뜻 |
|---|---|
| Fast | 어떤 테스트도 기다리지 않는다. 시간·프로세스·예약 실행을 기다려야 하면 가짜를 주입한다 |
| Independent | 실제 환경, 사용자 홈, 공유 파일을 건드리지 않는다. 임시 폴더는 시나리오마다 새로 만든다 |
| Repeatable | 운영체제에 따라 다른 동작은 값을 넘겨 확인하고, 실제 기기를 읽지 않는다 |
| Self-validating | 사람이 출력을 읽고 판단해야 하는 테스트는 없다 |
| Timely | 옮기기 전에 동작을 먼저 고정한다. 그래야 테스트가 이동을 지켜준다 |

### 무작위 데이터

Instancio는 그 시나리오가 신경 쓰지 않는 필드만 채웁니다. 검증 대상 값은 반드시 직접 지정합니다. 이렇게
하면 무작위 채우기가 재현성을 깨지 않고, 그 시나리오가 무시하는 필드가 코드에 드러납니다.

에이전트 기록은 절대 생성하지 않습니다. 정확히 그 값이 무엇인지가 핵심인 고정 값입니다.

### 값을 적어 비교해도 되는 때

바깥과의 계약이면 기대값을 적어 비교해도 됩니다. 저장 키, 프로토콜 이름, 등록 식별자, 기본값처럼
개발자가 조용히 바꿀 수 있고 사용자가 알아채는 값입니다.

구현에서 상수를 가져와 같은 상수와 비교하면 안 됩니다. 값이 무엇이든 통과하기 때문입니다.

### 만들지 않는 테스트

게터, 데이터 클래스 동등성, 프레임워크 동작, 구현을 그대로 되읊는 목 검증. 실패했을 때 사용자가 겪는
문제를 말할 수 없으면 그 테스트는 제 몫을 못 하는 것입니다.

### 속성 테스트

두 개뿐입니다. 둘 다 그냥 두면 어긋날 두 모듈의 약속을 지킵니다. 경로 상대화와 복원, 그리고 줄 범위
표기와 그것을 되읽는 파서입니다.

### 테스트하지 않는 것

목록과 이유는 `docs/ko/architecture.md`의 "테스트하지 않는 것과 그 이유"에 있습니다.

## 자원 수명

호출 하나보다 오래 사는 것에는 주인과 해제 경로가 필요합니다. 리스너, 터미널 위젯, 브라우저, 타이머,
실행기, 브리지 세션, 백그라운드 작업이 모두 해당합니다.

| 규칙 | 이유 |
|---|---|
| 자원을 만든 자리에서 해제도 등록한다 | 둘을 떨어뜨리면 주인 없는 자원이 생긴다 |
| 도구 창이 아니라 모드 해제 담당자에 붙인다 | 화면이 자기가 그린 창보다 오래 살면 안 된다 |
| 자원을 감싼 쪽이 정리한다 | 조립 지점은 정리를 촉발하는 담당자만 가진다 |
| 프로젝트 참조를 세션보다 오래 들고 있지 않는다 | 닫힌 프로젝트가 살아남는다 |

터미널 완료 어댑터는 IDE 시스템 폴더 아래에 크기가 고정된 파일 묶음으로 둡니다. 터미널 모드는 인증된
브리지 세션만 소유합니다. 완료 주소와 실제 실행 파일 경로는 그 터미널 환경에만 있으며, 모드를 해제하면
세션이 사라져 고정 어댑터 파일도 아무 일도 하지 못합니다. 파일 안에는 프로젝트, 토큰, 대화 값을 넣으면
안 됩니다.

## 수동 확인

실제 IDE가 있어야 확인되는 것이 있습니다. 도구 창, 화면, 설정을 건드린 변경을 내보내기 전에
`./gradlew runIde`로 아래를 확인합니다.

- 도구 창이 오른쪽에 열리고 터미널 모드로 에이전트가 뜬다
- 에이전트 선택 상자에 넷이 모두 보이고, 다른 것을 고르기 전까지 Change가 꺼져 있다
- 에이전트 전환과 모드 전환을 반복해도 정상이고, 로그에 오류가 없다
- 이전 버전이 저장한 설정이 그대로 읽히고, 에이전트별 경로가 서로 섞이지 않는다
- 파일, 선택 영역, 프로젝트 목록 선택을 컨텍스트에 추가하면 에이전트에 전달된다
- 설치되지 않은 에이전트에서 안내가 뜨고, Install을 누르기 전에는 아무것도 실행되지 않는다
- 웹 화면이 로딩되고, 파일 링크를 누르면 맞는 줄에서 열린다
- OpenCode 웹, 지원하는 직접 TUI 각각, Terminal에서 이름으로 실행한 지원 에이전트 각각에서 메인
  에이전트 응답 하나를 끝내거나 구조화된 질문 UI를 열면 IntelliJ가 활성 상태여도 IntelliJ 풍선과 OS
  네이티브 팝업이 함께 생긴다
- 안정된 Codex `request_user_input` 훅을 `/hooks`에서 신뢰한 뒤, 훅 신뢰를 우회하지 않고 Codex 질문
  알림이 생기는지 확인한다
- 터미널 모드를 닫거나 바꾸면 예전 완료 주소가 인증 거부되고, AgentellIJ 밖에서 띄운 에이전트는
  AgentellIJ 알림을 만들지 않는다
- IDE를 닫을 때 오류가 없다

## 문서

`docs/`에는 범위가 겹치지 않는 문서 넷이 있습니다. 이 문서와 `docs/ko/overview.md`,
`docs/ko/architecture.md`, `docs/ko/contracts.md`입니다. 저장소 최상위의 `AGENTS.md`가 AI 에이전트를 맞는
문서로 안내합니다.

영어가 정본입니다. `docs/ko/`에 각각의 한국어 번역이 있고 절 구성이 같습니다. 영어 문서를 고쳤으면 짝이
되는 한국어 문서를 맞출 때까지 작업이 끝난 것이 아닙니다.

`README.md`는 플러그인을 설치하는 사용자를 위한 것이고, `docs/`는 플러그인을 고치는 사람을 위한
것입니다.

변경 로그를 작성하거나 수정하기 전에 `changelogs/`의 모든 파일을 읽습니다. 현재형 동사로 시작하는
문장으로 사용자가 알아야 할 구체적 변경을 쓰고, `<li>` 하나에는 응집된 변경 하나만 담으며, 문장 끝에
마침표를 붙이지 않습니다.

끝내지 못한 일은 문서가 아니라 이슈에 적습니다. 이전 구조 문서에는 지키지 못한 항목 목록이 있었고
스물다섯 개까지 자랐지만 대부분 닫히지 않았습니다. 그런 목록은 의도만 기록할 뿐 실행을 압박하지
않습니다.
